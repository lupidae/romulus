Every version kept. Any two compared.

Each upload, import, CI push and published draft becomes a version that can't be edited afterwards. Pick any two to see what changed, as a list, on the graph and in SQL, and get the migration between them.

  • Diffs of the schema itselfA column that became NOT NULL shows up. Reformatting the SQL shows nothing.
  • A history nobody rewritesEach version records who made it and where it came from. An admin can remove one: it stays restorable for 30 days, and the audit log keeps who did it and why.

Design the next version together.

A draft is a branch of your schema the whole team can open at once. Type SQL or work on the graph; both edit the same draft, and everyone's cursor shows in both. If a new version lands first, Update draft merges it statement by statement.

  • Checked by Postgres as you typeEach change compiles in a sandbox running the database's own Postgres version, and errors point at the line that caused them.
  • Edit on the graph, get SQLRename, add or drop tables and columns, or draw a foreign key, and romulus writes the statement. Group tables by area, give each group a color, and drag a group as one.
  • Write the schema, or write the migrationEdit the SQL and the migration is generated for you. Or switch the draft to writing the migration by hand: the schema and the graph follow from it.

Review the change where it's made.

Comment on a table, a column, a statement or any spot on the graph. In the SQL, a thread shows as a --- line above the statement it's about, and it follows a rename.

  • Start a thread by typingWrite a --- line above a statement and press Enter. Reply, mention a teammate with @, and resolve it once it's settled.
  • Approvals your organization setsAsk for up to 10 approvals from members who didn't edit the draft. Any edit resets them. An admin can publish without them by giving a reason, which is logged.
  • The discussion stays with the versionPublishing keeps the threads as review history. They never turn into COMMENT ON in your schema.

Bring your migrations. Get the next one written.

Import the history you already have, one version per migration. Then each change you design comes out as files for the tool you run, ready to review.

  • Import the history you haveFolders of plain SQL migrations (sqlx, dbmate, golang-migrate, node-pg-migrate), Flyway and Prisma. Rails, Django and Alembic come in through the SQL they print. Data statements are skipped and listed.
  • Files for your toolPlain SQL, sqlx, Flyway, Prisma, dbmate or golang-migrate, named the way each one expects, with a down migration for the tools that have one.
  • Risks marked before anyone runs itThe file marks each statement that deletes data, can fail on existing rows, or widens access through row level security.

Try the migration on rows first.

A playground is a real Postgres holding a version's schema, filled with generated rows. Everyone on the team can query it, and developers run the draft's migration on it to see what each statement does.

  • A console for the whole teamReviewers query too, read-only: Postgres privileges enforce it. Results, plans and a history everyone shares.
  • Run the migration, then resetSee each statement's locks, rewrites and timing. A failure comes with Postgres's error and the rows that broke it. Reset puts the generated rows back.
  • Isolated and syntheticEach playground runs in its own gVisor container, with no network and no superuser. Its rows are generated from the schema, never copied from yours.

Push the real schema from CI.

remus, the open-source twin of romulus, reads your database's catalog inside your own pipeline and sends the result. romulus never sees a connection string or a row of data.

  • Push on every runWhen nothing changed, the push answers 200 unchanged and the history stays clean.
  • Import migrations from CI tooThe same token sends your migrations folder. Only migrations romulus hasn't seen become versions, and a changed one is refused.
  • Tokens with one jobA push token belongs to one database and can only push and import.
In CI, after your migrations 
remus -u "$DATABASE_URL" -f json \  | curl -fsS --data-binary @- \      -H "Authorization: Bearer $ROMULUS_TOKEN" \      -H "Content-Type: application/json" \      "$ROMULUS_URL/api/databases/$ROMULUS_DATABASE_ID/versions"

Your agent speaks romulus.

romulus has an MCP server built in, at /api/mcp: nothing to install. Claude Code, Claude Desktop, claude.ai, Cursor or any MCP client works in romulus the way you do.

  • From a question to a published versionIt reads schemas, versions and diffs, and searches across databases. It drafts a change, gets its migration with renames detected, tests it up and down in a playground, then requests review and publishes.
  • A new database from a dumpHand it a pg_dump --schema-only or remus's output: it creates the database with that first version, then hands you the CI step that keeps it current.
  • It acts as you, with your roleA read-only token can't change anything. Approvals, required tests and the rules for publishing apply to agents too.
Add romulus to Claude Code 
claude mcp add --transport http romulus https://romulus.lupidae.com/api/mcp

Then run /mcp and sign in with your browser. Other clients take the same URL. For CI and headless agents, use an access token. A self-hosted romulus has the same endpoint at its own address.

Postgres, down to the last policy.

romulus keeps what the Postgres catalog says, with remus's model. Each database targets one Postgres version: its drafts compile in that version's sandbox, so the graph shows what Postgres accepted, and its migrations are written for it.

  • PostgreSQL 18
  • PostgreSQL 17default
  • PostgreSQL 16
  • PostgreSQL 15
  • ENUMEnums, with their values in order
  • DOMAINDomains, with their base type and checks
  • PARTITION BYPartitioned tables, partitions kept under their parent
  • CREATE POLICYRow level security policies and their roles
  • GENERATEDIdentity and generated columns
  • CHECKCheck, unique and exclusion constraints
  • WHEREPartial and expression indexes
  • COMMENT ONComments on tables and columns, shown on the graph
  • CREATE VIEWViews, with the tables they read
  • citext[]Arrays and composite types

Moving a database to another Postgres version is a dry run first: its latest version has to compile there before anything changes.

Roles, functions and extensions your SQL uses without creating are stubbed for the compile, and never reach your model.

Roles that match how teams review.

Each organization has three roles. Reviewers see every version, follow drafts live, comment, approve and query playgrounds, without editing anything. Their cursor stays visible, so you know who's looking.

  • Read-only, enforced by the serverA reviewer's edits are dropped before they reach the draft, and a playground's console only reads.
  • Single sign-on, invite linksAn invitation works once, and only for the verified email it was made for.

How to self-host

Run it on your own servers.

Open source under the AGPL-3.0: the whole product, free, for one organization per install. Your schemas and discussions stay on machines you run.

  • What it needsDocker and 4 GB of memory, 8 GB with other Postgres versions and playgrounds. Playgrounds need Linux, gVisor and an XFS volume. See the requirements.
  • One script runs itIt installs, upgrades, backs up every night and restores. People sign in with an email and a password, or through your own identity provider.
Read the self-host docs lupidae/romulus

Later, an enterprise license (the ee/ directory) will add SAML and SCIM single sign-on, audit-log export and advanced approval rules. The open-source product never depends on it.

Docker, on one host 
git clone https://github.com/lupidae/romulus.gitcd romulus/deploy/self-host./install.sh

It checks the host, asks for the URL, the first admin, mail and playgrounds, starts everything and prints a link to set your password.

Kubernetes, with Helm 
helm install romulus oci://ghcr.io/lupidae/charts/romulus \  --namespace romulus --create-namespace \  --set host=romulus.example.com

The installer's images and settings, without playgrounds yet. TLS, an external Postgres, upgrades and backups: the Kubernetes guide.

From source 
git clone https://github.com/lupidae/romulus.git && cd romulusdocker build -t local/romulus-api:dev .docker build -t local/romulus-sandbox:dev deploy/sandboxcd deploy/self-host./install.sh --registry local --version dev --no-pull

Your own images, for an arm64 host or your own changes. Playgrounds need two more: the Dockerfile's play target and deploy/playground.

Questions

Something else? Write to us.

What does “DBA as a service” mean here?

romulus does the schema work a DBA would keep for a team: it keeps every version, shows exactly what changed, checks each proposal in real Postgres, writes the migration for your tool and lets you try it on generated rows, all before anyone publishes it.

Does romulus connect to our production database?

No. You upload SQL or migration files, or remus reads your database inside your own CI and pushes the schema. romulus never holds a connection string and never sees your data.

Does it replace our migrations?

No, it works with them. Import the history you have and keep running your tool: each change you design comes out as a migration file for it, plain SQL, sqlx, Flyway, Prisma, dbmate or golang-migrate.

Does it work with my AI agent?

Yes. romulus has an MCP server built in, so Claude Code, Claude Desktop, claude.ai, Cursor or any MCP client can read your schemas, draft a change, generate and test its migration, and ask for a review. It acts as you, with your role, and your organization's rules apply. See how to connect it.

Which is the source of truth, the SQL or the graph?

The SQL. Edits on the graph are written back as SQL statements, so the text is always what gets compiled and versioned. In a draft where you write the migration by hand, the migration is that text and the schema follows from it. Table positions and groups are saved next to it.

Which Postgres versions does it understand?

15, 16, 17 and 18. Each database targets one, 17 by default: its drafts compile in that version's sandbox and its migrations are written for it. Pushes from remus carry whatever your own server's catalog says. Playgrounds run PostgreSQL 17 for now.

What data is in a playground?

Rows romulus generates from the schema, realistic values or edge cases, that respect its types, keys, checks and enums. Nothing comes from your database. The same seed gives the same rows, so a playground can always be built again.

Do comments end up in our schema?

No. Threads are review history: they stay with the draft, then with the version it becomes. They never turn into COMMENT ON, and a --- line never stays in the SQL.

How do people sign in?

With single sign-on. An admin invites teammates with a one-time link, which only works for the verified email address it was made for. A self-hosted romulus also signs people in with an email and a password.

What does it cost?

The hosted plans are in Pricing: a free one for one person, then flat monthly or yearly prices with unlimited members, for businesses and professionals. Every organization starts on Free, and an admin moves it to a paid plan from its Billing page whenever it needs more. Self-hosting is free.

What happens when we reach a cap?

Nothing is deleted, and everything you have keeps working. Only adding more of what is capped waits, a database or a version for example, until you make room or move to a larger plan. Playground hours are the only metered resource: once a month's hours are used, playgrounds wait for the next month or a larger plan.

Is it really open source?

Yes. The API, the web app, the sandboxes and the playgrounds are all in the public repository, under the AGPL-3.0, and a self-hosted install is the whole product. Paid features for larger companies will come later under a separate license, in the repository's ee/ directory; the open-source product never depends on them.

Can we host it ourselves?

Yes, free, for one organization per install: on one host with Docker, on Kubernetes with Helm, or built from source. See the three ways, or read the self-host docs.

Can we move from hosted to self-hosted?

Yes. On every plan, an admin can export the whole organization as one ZIP: every version's SQL, the migrations between versions, open drafts and every comment. Any member can export a single database. remus pushes your schema from CI to any romulus, hosted or your own, and a folder of migrations imports the same way.
