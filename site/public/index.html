Design the next version together.

A draft is a branch of your schema the whole team can open at once. Type SQL or work on the graph; both edit the same draft, and everyone's cursor shows in both. If a new version lands first, Update draft merges it statement by statement.

  • Checked by Postgres as you typeEach change compiles in a sandbox running the database's own Postgres version, and errors point at the line that caused them.
  • Edit on the graph, get SQLRename, add or drop tables and columns, or draw a foreign key, and romulus writes the statement. Group tables by area, give each group a color, and drag a group as one.
  • Write the schema, or write the migrationEdit the SQL and the migration is generated for you. Or switch the draft to writing the migration by hand: the schema and the graph follow from it.

Review the change where it's made.

Comment on a table, a column, a statement or any spot on the graph. In the SQL, a thread shows as a --- line above the statement it's about, and it follows a rename.

  • Start a thread by typingWrite a --- line above a statement and press Enter. Reply, mention a teammate with @, and resolve it once it's settled.
  • Approvals your organization setsAsk for up to 10 approvals from members who didn't edit the draft. Any edit resets them. An admin can publish without them by giving a reason, which is logged.
  • The discussion stays with the versionPublishing keeps the threads as review history. They never turn into COMMENT ON in your schema.

Try the migration on rows first.

A playground is a real Postgres holding a version's schema, filled with generated rows. Everyone on the team can query it, and developers run the draft's migration on it to see what each statement does.

  • A console for the whole teamReviewers query too, read-only: Postgres privileges enforce it. Results, plans and a history everyone shares.
  • Run the migration, then resetSee each statement's locks, rewrites and timing. A failure comes with Postgres's error and the rows that broke it. Reset puts the generated rows back.
  • Isolated and syntheticEach playground runs in its own gVisor container, with no network and no superuser. Its rows are generated from the schema, never copied from yours.

Push the real schema from CI.

remus, the open-source twin of romulus, reads your database's catalog inside your own pipeline and sends the result. romulus never sees a connection string or a row of data.

  • Push on every runWhen nothing changed, the push answers 200 unchanged and the history stays clean.
  • Import migrations from CI tooThe same token sends your migrations folder. Only migrations romulus hasn't seen become versions, and a changed one is refused.
  • Tokens with one jobA push token belongs to one database and can only push and import.

Postgres, down to the last policy.

romulus keeps what the Postgres catalog says, with remus's model. Each database targets one Postgres version: its drafts compile in that version's sandbox, so the graph shows what Postgres accepted, and its migrations are written for it.

  • PostgreSQL 18
  • PostgreSQL 17default
  • PostgreSQL 16
  • PostgreSQL 15
  • ENUMEnums, with their values in order
  • DOMAINDomains, with their base type and checks
  • PARTITION BYPartitioned tables, partitions kept under their parent
  • CREATE POLICYRow level security policies and their roles
  • GENERATEDIdentity and generated columns
  • CHECKCheck, unique and exclusion constraints
  • WHEREPartial and expression indexes
  • COMMENT ONComments on tables and columns, shown on the graph
  • CREATE VIEWViews, with the tables they read
  • citext[]Arrays and composite types

Moving a database to another Postgres version is a dry run first: its latest version has to compile there before anything changes.

Roles, functions and extensions your SQL uses without creating are stubbed for the compile, and never reach your model.

Each organization has three roles. Reviewers see every version, follow drafts live, comment, approve and query playgrounds, without editing anything. Their cursor stays visible, so you know who's looking.

Questions

Something else? Write to us.

What does “DBA as a service” mean here?

romulus does the schema work a DBA would keep for a team: it keeps every version, shows exactly what changed, checks each proposal in real Postgres, writes the migration for your tool and lets you try it on generated rows, all before anyone publishes it.

Does romulus connect to our production database?

No. You upload SQL or migration files, or remus reads your database inside your own CI and pushes the schema. romulus never holds a connection string and never sees your data.

Does it replace our migrations?

No, it works with them. Import the history you have and keep running your tool: each change you design comes out as a migration file for it, plain SQL, sqlx, Flyway, Prisma, dbmate or golang-migrate.

Which is the source of truth, the SQL or the graph?

The SQL. Edits on the graph are written back as SQL statements, so the text is always what gets compiled and versioned. In a draft where you write the migration by hand, the migration is that text and the schema follows from it. Table positions and groups are saved next to it.

Which Postgres versions does it understand?

15, 16, 17 and 18. Each database targets one, 17 by default: its drafts compile in that version's sandbox and its migrations are written for it. Pushes from remus carry whatever your own server's catalog says. Playgrounds run PostgreSQL 17 for now.

What data is in a playground?

Rows romulus generates from the schema, realistic values or edge cases, that respect its types, keys, checks and enums. Nothing comes from your database. The same seed gives the same rows, so a playground can always be built again.

Do comments end up in our schema?

No. Threads are review history: they stay with the draft, then with the version it becomes. They never turn into COMMENT ON, and a --- line never stays in the SQL.

How do people sign in?

With single sign-on. An admin invites teammates with a one-time link, which only works for the verified email address it was made for. A self-hosted romulus also signs people in with an email and a password.

What does it cost?

Nothing during early access, since there is no billing yet. Request access and we'll set up your organization.

Can we host it ourselves?

Yes. romulus is open source (AGPL-3.0) and free to run for one organization: the whole product, on one Linux host with Docker, installed by one script that asks the few things it needs. Read the self-hosting guide.
