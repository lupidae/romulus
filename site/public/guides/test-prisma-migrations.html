How to test Prisma migrations before they reach production

Run each new migration.sql on a database that has rows, in CI, before the pull request merges. Prisma's own checks don't do that: prisma migrate dev warns about data loss from what your development database happens to hold, and prisma migrate deploy applies the files without checking them. So a required column, a unique index or a narrowed enum passes on your laptop's empty tables and fails on production's rows. Below: what Prisma checks, what breaks on rows, and a real run of romulus test catching it from a Prisma folder.

Written October 24, 2026, for Prisma ORM 7 (7.10.1) and PostgreSQLSources

What Prisma checks, and what it doesn't

  • prisma migrate dev replays your migration history in a shadow database (a temporary one it creates and deletes) to detect drift, generates the new migration, and warns about data loss before applying it: “You are about to drop the column … All the data in the column will be lost”, or “Added the required column … without a default value … This is not possible if the table is not empty.” The warnings are about the current datasource, your development database: on empty tables you get the generic wording, not the rows it would break. It is for development only, and stops in a non-interactive shell such as CI.
  • prisma migrate deploy, the command for CI and production, applies pending migrations. Its documentation says it does not look for drift or changes in the Prisma schema and does not use a shadow database; the one warning it documents is a migration modified after it was applied.
  • prisma migrate diff --exit-code compares two states, for instance --from-migrations prisma/migrations --to-schema prisma/schema.prisma, and exits 2 when they differ: a good CI check that the migrations match schema.prisma. It compares schemas, not data. (In Prisma 7, --to-schema-datamodel became --to-schema and the --from-url, --to-url and --shadow-database-url options gave way to the datasource in prisma.config.ts.)
  • prisma migrate status exits 1 when migrations are unapplied, failed, or the history diverged: useful before a deploy.

None of these runs a new migration against rows shaped like production's. That is the check to add.

What breaks on rows

  • A required field added to a model with rows. Prisma writes ALTER TABLE "User" ADD COLUMN "phone" TEXT NOT NULL;, which Postgres refuses on a table that has rows (error 23502). Add it optional, backfill, then make it required, or give it a default.
  • A new @unique on a column with duplicates: the index build fails. Prisma's own warning says “If there are existing duplicate values, this will fail.”
  • An enum value removed while rows still use it: “If these variants are still used in the database, this will fail.”
  • A rename: Prisma's docs say renaming a field produces a migration that creates the new column and drops the old one, with its data. Edit the generated file (--create-only) to RENAME COLUMN.
  • An @@index on a busy table: CREATE INDEX without CONCURRENTLY holds a lock that makes every write to the table wait until the index is built. It succeeds, so no test that only checks for errors sees it.

A CI step that runs the new migrations on rows

You can build it yourself: a Postgres service in the CI job, a schema and rows that look like production (a sanitized dump, or a seed you maintain), prisma migrate deploy, then queries that check what you care about. It works; the cost is keeping the rows realistic as the schema grows.

Or use romulus test, the command line of romulus (open source, also a GitHub Action). Import your prisma/migrations folder into a romulus database once; then, on each pull request, it sends the folder, keeps only the migrations romulus has not imported, and runs them on a playground: a Postgres 17 holding your latest version and generated rows. It fails the job on a statement that fails, on a table rewrite or an index build that blocks writes, and on data that changes without a statement saying so.

.github/workflows/migrations.yml 
name: Migrationson:  pull_request:    paths: ["prisma/migrations/**"]jobs:  test:    runs-on: ubuntu-latest    steps:      - uses: actions/checkout@v7      - uses: lupidae/romulus@v0.3.0        with:          migrations: prisma/migrations          database: acme/shop          token: ${{ secrets.ROMULUS_TOKEN }}

The token is a personal access token with write access. docs/cli.md has the import on main, other CI systems and every option.

A real run

We ran it on October 24, 2026, against a local install of romulus: a shop database whose two Prisma migrations (init, orders) were imported, and a pull request adding two more, as prisma migrate dev writes them:

The pull request's two migrations 
-- prisma/migrations/20261020090000_user_phone/migration.sql
-- AlterTable
ALTER TABLE "User" ADD COLUMN     "phone" TEXT NOT NULL;

-- prisma/migrations/20261021090000_order_user_status_index/migration.sql
-- CreateIndex
CREATE INDEX "Order_userId_status_idx" ON "Order"("userId", "status");
