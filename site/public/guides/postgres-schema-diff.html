How to diff two Postgres schemas

Compare what Postgres made of each schema, not the text you wrote. You can point a tool at two live databases (pgAdmin's Schema Diff, migra, pgquarrel), let a tool load SQL files into a scratch database and compare the catalogs (Atlas, pg-schema-diff, supabase db diff), or keep every version in romulus, which compiles each one in a sandboxed Postgres and shows any two side by side: as a list of changes, on the table graph, and as SQL, with the migration between them. A text diff of two pg_dump --schema-only files works in a pinch, with the flags below to cut its noise.

Written October 24, 2026, against PostgreSQL 18's documentation and each tool's own pagesSources

The quick way: two dumps and diff

Dump the schema of each database as plain SQL, without the lines that differ for reasons other than the schema, then compare the files:

Two schemas, as text 
pg_dump --schema-only --no-owner --no-privileges \  --restrict-key=diff "$OLD_URL" > old.sqlpg_dump --schema-only --no-owner --no-privileges \  --restrict-key=diff "$NEW_URL" > new.sqldiff -u old.sql new.sql
  • --no-owner and --no-privileges leave out the ALTER … OWNER and GRANT lines, which differ between environments.
  • --restrict-key fixes the key of the \restrict line recent versions of pg_dump write; without it the key is random, so every dump differs on that line.
  • What it can't tell you: pg_dump sorts objects by type, then by name, and prints columns in their physical order, so a column added later sits last in one dump and wherever you wrote it in the other. A rename reads as one table removed and another added. And the output is a text diff, not a migration.

Tools that compare the catalog

These read what Postgres knows (columns, types, constraints, indexes, and, depending on the tool, views, functions, policies) and say what differs, most of them as the SQL that gets from one to the other.

Most need a connection to a running database, and some a second, empty one they can write to. That is fine on a laptop; in CI or against production it means credentials and network access. romulus works from SQL text alone: it never connects to your database.

Diffing in romulus

  1. Create a database (Postgres 15, 16, 17 or 18) and give it its versions: upload SQL (a pg_dump --schema-only works as is), import your migrations folder, or push from CI with remus.
  2. On the History tab, pick two versions and open the comparison. The address keeps both numbers (…/diff/1...2), so a link to it is the review.
  3. Read it as a list of changes, on the graph (added, removed and changed tables and columns, colored and labelled), or as the two SQLs merged. The Migration view gives the SQL that gets from one to the other, for plain SQL, sqlx, Flyway, Prisma, dbmate or golang-migrate.

Because both sides are compiled models, a reformatted file or reordered statements show no change, while a column becoming NOT NULL or a default changing does. Renames are detected and scored, and you choose which ones the migration applies.

What to look for in a schema diff

  • Renames that read as drop and add. A tool that compares by name drops the old column and adds a new, empty one. pg-schema-diff says so in its README; check any generated migration for a DROP COLUMN next to an ADD COLUMN of the same type.
  • Changes that fail on rows. A new NOT NULL, a unique index, a narrower type or a check constraint is a one-line diff and an error on the first row that breaks it. romulus marks those statements, and, for a database targeting Postgres 17, can run the migration on generated rows (how, with Prisma).
  • What your tool leaves out. Views, functions, triggers, policies and extensions are not compared by every tool (or edition). A diff that shows nothing has only compared what it reads.
  • The Postgres major. The same SQL can mean different things on 15 and 18; pgAdmin requires both servers on the same major. romulus compiles each database on the major it targets.
